# Правила работы агента

## Работа с задачей

- Перед изменениями изучать затронутый код, [техническое задание](./0-tech-spec.md),
  [технологии, архитектуру и стиль кода](./01-code-style.md)
  и [бизнес-логику](./03-business-logic.md).
  Для запросов — [контракт GREEN-API](./04-green-api-contract.md), для вёрстки — [интерфейс](./05-ui.md).
- Следовать актуальным указаниям пользователя. Если они меняют договорённости, обновлять соответствующую документацию.
- Реализовывать функциональность в пределах задачи. Не добавлять зависимости, экраны и возможности «на будущее».
- Сохранять существующие изменения пользователя. Не включать в задачу несвязанные исправления и массовое форматирование.
- Обычные технические решения принимать самостоятельно. Уточнять только то, что существенно влияет на результат
  и не определяется задачей или спецификациями.

## Организация кода

- Выносить повторяющиеся части интерфейса с одинаковым назначением в отдельные компоненты.
  Не объединять разные по смыслу элементы только из-за похожей разметки.
- Повторяющуюся логику состояния и эффектов React выносить в пользовательские хуки.
  Преобразование данных, валидацию и другие вычисления без React оформлять обычными функциями.
- Разделять отображение интерфейса, работу с API и обновление состояния по архитектуре проекта.
  Компоненты не должны самостоятельно собирать URL запросов GREEN-API.
- Использовать понятные имена. Комментариями объяснять причины неочевидных решений, а не пересказывать код.
- Типизировать props, состояние, события и ответы API. Для неизвестных данных использовать `unknown` с проверками.
  Не скрывать ошибки типов через необоснованные `any`, приведения типов или отключение проверок.

## React и состояние

- Хранить состояние у ближайшего общего владельца. Значения форм оставлять локальными,
  а связанные изменения чатов и сообщений обрабатывать через reducer.
- Не хранить отдельно значения, которые можно вычислить из существующего состояния и props.
- Сохранять reducer чистым: без запросов, таймеров и изменения исходных объектов.
  Не мутировать состояние React.
- Использовать эффекты для синхронизации с внешними системами. Очищать запросы, таймеры и подписки при завершении.
  Учитывать повторный запуск и очистку эффектов в React Strict Mode.
- Использовать устойчивые идентификаторы в `key` для чатов и сообщений, чтобы сохранять связь элемента с его состоянием.
- Применять `Suspense`, когда есть поддерживаемый им источник загрузки, например компонент через `React.lazy`.
  Для обычных запросов через `fetch` в эффектах и обработчиках явно управлять состояниями загрузки и ошибки:
  `Suspense` такие запросы не отслеживает. Не вводить ленивую загрузку только ради использования `Suspense`.
  Основание: [документация React](https://react.dev/reference/react/Suspense).

## Интерфейс

- Следовать [интерфейсу](./05-ui.md) и минимальному набору функций из ТЗ.
  Стили компонентов хранить в CSS Modules, общие значения цветов и размеров — в CSS-переменных.
- Использовать семантические элементы: кнопки для действий, формы для ввода, подписи для полей.
  Обеспечивать управление с клавиатуры и видимый фокус; кнопкам без текста задавать доступное название.
- Предусматривать пустую переписку, ожидание отправки и ошибки. Сообщения об ошибках должны быть понятны пользователю.
- Отображать текст сообщений как текст React, без вставки непроверенного HTML через `dangerouslySetInnerHTML`.

## Работа с GREEN-API

- Сверять методы с [контрактом](./04-green-api-contract.md) и официальной документацией GREEN-API для Telegram.
  При расхождении документации и ТЗ отмечать его явно; не переносить контракты WhatsApp или MAX по аналогии.
- Выполнять запросы через общий модуль на `fetch`. Различать HTTP-ошибки, сетевые сбои и отмену запроса.
  Обрабатывать пустые ответы там, где они предусмотрены API.
- Соблюдать последовательность получения и подтверждения уведомлений из описания архитектуры.
  Защищаться от дублей; известные неподдерживаемые события осознанно пропускать и подтверждать,
  чтобы они не блокировали очередь.
- При временных сбоях получения делать задержку перед повтором. Ошибки учетных данных или настроек
  показывать пользователю, не повторяя запросы бесконечно без возможности исправления.
- Привязывать результаты отправки к исходному чату и сообщению, даже если пользователь переключил чат.
  Сохранять введённый текст при ошибке и исключать случайную повторную отправку.
- При выходе отменять активные запросы и исключать применение ответов предыдущей сессии.
- Хранить учетные данные только в памяти согласно архитектуре. Не помещать токен в исходники,
  логи, тестовые фикстуры и сообщения об ошибках; учитывать, что URL GREEN-API содержит токен.

## Проверка результата

- Подбирать проверки по характеру изменения. Покрывать тестами значимую логику и поведение,
  особенно обработку уведомлений, ошибки отправки, переключение чатов и завершение сессии.
- В тестах компонентов проверять пользовательские действия и видимый результат.
  Не привязывать проверки к внутренним переменным компонентов и сгенерированным CSS-классам.
- В автоматических тестах подменять ответы API и использовать фиктивные учетные данные.
  Тесты не должны отправлять реальные сообщения или зависеть от доступности GREEN-API.
- После изменений кода запускать применимые проверки из проекта: TypeScript, ESLint, Prettier,
  тесты и сборку. Исправлять обнаруженные проблемы в пределах задачи.
- Изменения интерфейса проверять в браузере, когда он доступен. Проверять переписку и доступность элементов
  при изменении ширины окна. Успешные тесты в jsdom не заменяют визуальную проверку.
- В итоговом сообщении кратко указывать, что изменено, что проверено и что осталось непроверенным.
  Не заявлять об успешных проверках, которые не выполнялись.
