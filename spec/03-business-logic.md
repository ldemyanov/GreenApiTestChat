# Бизнес-логика приложения

Документ раскрывает [техническое задание](./0-tech-spec.md) и описывает поведение приложения.
Технологии и организация кода определены в [описании архитектуры](./01-code-style.md).
Форматы запросов — в [контракте GREEN-API](./04-green-api-contract.md), экраны и тексты — в [интерфейсе](./05-ui.md).
Правила ниже конкретизируют минимальный сценарий: подключение, создание личного чата и обмен текстом.

## Функциональность и границы версии

- Подключение к одному инстансу GREEN-API с учетными данными пользователя.
- Создание личного чата по номеру телефона и переключение между созданными чатами.
- Отправка текстовых сообщений и отображение входящих ответов в соответствующей переписке.
- Отображение ожидания и результата отправки, ошибок подключения и получения сообщений.
- Выход из приложения с очисткой локальной сессии.

Чаты, сообщения и черновики доступны только в текущей сессии браузерной вкладки.
Обновление страницы сбрасывает данные. Полную историю из Telegram не загружаем:
в переписке отображаются сообщения, отправленные приложением или полученные из очереди в этой сессии.
Уведомления в очереди могут относиться к сообщениям, пришедшим до входа пользователя.

Групповые чаты, вложения, редактирование и удаление сообщений, синхронизация прочтения и импорт контактов
не входят в текущую версию. Внешний вид MAX используется как образец интерфейса; обмен сообщениями идёт через Telegram.

## Условия работы

Пользователь заранее создаёт инстанс и авторизует Telegram в личном кабинете GREEN-API.
Для получения сообщений через HTTP API нужны пустой `webhookUrl` и включённый `incomingWebhook`.
Приложение использует подготовленный инстанс и не меняет эти настройки автоматически.
Основание: [получение уведомлений через HTTP API](https://green-api.com/telegram/docs/api/receiving/technology-http-api/).

Для тестирования одну очередь инстанса должен обрабатывать один активный клиент.
Параллельные вкладки или другие потребители этой очереди не входят в поддерживаемый сценарий.

## Роли пользователей и права

В приложении одна пользовательская роль. Доступность действий зависит от наличия активной сессии.

| Участник или состояние | Доступные действия |
| --- | --- |
| Пользователь до подключения | Ввести учетные данные и выполнить подключение |
| Пользователь с активной сессией | Создавать и выбирать чаты, отправлять текст, видеть входящие сообщения, выйти |
| Собеседник в Telegram | Получать сообщения и отвечать через свой Telegram; доступ к веб-приложению ему не нужен |

Собственной регистрации, администратора и системы назначения прав нет.
GREEN-API проверяет доступ по учетным данным инстанса. Скрытие элементов интерфейса не заменяет эту проверку.
Смена учетных данных начинает новую сессию; переписка предыдущего инстанса в неё не переносится.

## Сущности и зависимости

| Сущность | Основные данные | Связи и назначение |
| --- | --- | --- |
| Сессия | Локальный идентификатор сессии, `idInstance`, `apiTokenInstance`, состояние подключения | Владеет чатами и одним циклом получения уведомлений |
| Чат | `chatId`, известный номер телефона, отображаемое имя | Принадлежит сессии и содержит сообщения одного собеседника |
| Сообщение | Локальный идентификатор, `chatId`, `idMessage` при наличии, текст, направление, время, состояние отправки | Принадлежит ровно одному чату |
| Черновик | `chatId`, введённый текст | Сохраняет незавершённый ввод конкретного чата в текущей сессии |
| Уведомление API | `receiptId`, тип события, тело события | Доставляет событие и требует подтверждения обработки; не является сообщением само по себе |

Номер телефона, `chatId`, `idInstance` и `idMessage` в модели храним строками.
Приведение к числовому типу выполняем только на границе API, если этого требует конкретный метод.
Активный чат — ссылка на существующий `chatId` либо отсутствие выбора; отдельную копию его сообщений не создаём.

## Пользовательские сценарии

### Подключение

1. Пользователь вводит `idInstance` и `apiTokenInstance`.
2. Удаляем пробелы по краям. Проверяем заполненность полей и то, что `idInstance` состоит из цифр.
   Регистр и внутреннее содержимое токена не изменяем.
3. Проверяем состояние инстанса через `GetStateInstance`. На время запроса блокируем повторное подключение.
4. При `stateInstance: authorized` создаём локальную сессию, открываем интерфейс чата и запускаем получение уведомлений.
5. При другом состоянии показываем причину недоступности и предлагаем подготовить инстанс в личном кабинете.
   При ошибке запроса оставляем форму доступной для исправления данных или повторной попытки.

Основание: [GetStateInstance](https://green-api.com/telegram/docs/api/account/GetStateInstance/).
Учетные данные остаются в памяти приложения и удаляются при завершении сессии.

### Создание и выбор чата

1. Пользователь вводит номер получателя в международном формате, включая код страны.
2. Удаляем пробелы, скобки, дефисы и один начальный `+`. Результат должен быть непустым,
   состоять из цифр и начинаться с ненулевой цифры. Код страны не подставляем
   и местные префиксы автоматически не заменяем. Не допускаем потери цифр при преобразовании номера для API.
3. Если этот нормализованный номер уже связан с чатом сессии, открываем существующую переписку.
4. Иначе по подтверждению формы вызываем `CheckAccount`, передавая `phoneNumber` числом согласно контракту API.
   Используем обычный режим с кэшем API, параметр `force` не включаем.
   Во время проверки повторное подтверждение недоступно; запросы на каждое нажатие клавиши не выполняем.
5. При `exist: true` и непустом `chatId` создаём локальный чат или открываем уже существующий с таким `chatId`.
   Сохраняем связь номера с идентификатором и выбираем этот чат.
6. При `exist: false` сообщаем, что найти доступный аккаунт по номеру не удалось.
   Причиной может быть отсутствие аккаунта или настройки приватности; не утверждаем, что Telegram у человека нет.
7. Ошибки и ограничения API показываем отдельно от результата поиска. При них чат не создаём, номер сохраняем.

Создание чата добавляет переписку в интерфейс и само по себе не отправляет сообщение собеседнику.
Для последующих отправок и сопоставления ответов используем полученный `chatId`.
Основание: [CheckAccount](https://green-api.com/telegram/docs/api/service/CheckAccount/)
и [идентификатор чата](https://green-api.com/telegram/docs/api/chat-id/).

Переключение чата меняет только выбранную переписку. Сообщения и черновики других чатов сохраняются в памяти,
а получение уведомлений продолжает работать на уровне всей сессии.

### Отправка сообщения

1. Пользователь вводит текст в выбранном чате и подтверждает отправку кнопкой или клавишей Enter.
   Shift+Enter добавляет перенос строки. Enter во время составного ввода текста через IME не отправляет сообщение.
2. Проверяем, что сессия активна, чат выбран, текст содержит непробельные символы и не превышает 4096 символов.
   Пробелы и переносы внутри допустимого сообщения сохраняем; текст автоматически не обрезаем и не разбиваем.
3. Фиксируем исходные `chatId`, текст и локальный идентификатор сообщения. Добавляем исходящее сообщение
   в состоянии `sending` и вызываем `SendMessage`.
4. Пока запрос выполняется, повторная отправка в этом чате недоступна. Переключение на другой чат разрешено.
5. При успешном ответе с `idMessage` обновляем исходное сообщение до состояния `accepted`.
   Очищаем соответствующий черновик только если пользователь с момента отправки не изменил его.
6. При явном отказе API устанавливаем `failed` и сохраняем текст для исправления.
   При обрыве соединения, таймауте или другом ответе, не позволяющем установить результат, ставим `unknown`.
7. Автоматически не повторяем отправку. Отдельной кнопки повтора у сообщения нет:
   текст остаётся в поле ввода, где пользователь может исправить его и снова нажать «Отправить».
   Для неопределённого результата объясняем, что сообщение уже могло быть отправлено.
8. Результат всегда применяется к исходному чату и сообщению, независимо от выбранной в этот момент переписки.

`SendMessage` помещает сообщение в очередь. Возвращённый `idMessage` подтверждает приём API,
но не доставку и не прочтение собеседником. Основание:
[SendMessage](https://green-api.com/telegram/docs/api/sending/SendMessage/).

| Состояние исходящего сообщения | Значение для пользователя |
| --- | --- |
| `sending` | Запрос отправки выполняется |
| `accepted` | Сообщение принято API к отправке |
| `failed` | Получен явный отказ, нужна корректировка или повторная попытка |
| `unknown` | Результат отправки не удалось подтвердить |

Эти состояния описывают запрос приложения. Отметки доставки и прочтения в этой версии не реализуем.

### Получение сообщений

1. В активной сессии выполняем один последовательный цикл `ReceiveNotification`.
   Пустой ответ означает отсутствие события, после него продолжаем ожидание.
2. Личным считаем уведомление с `senderData.chatType: "user"`.
   Для входящего личного текстового сообщения определяем чат по `senderData.chatId`.
   Отображаем сообщения только для чатов, созданных пользователем по номеру телефона в текущей сессии.
   Уведомления остальных чатов, включая ботов, пропускаем и подтверждаем через `DeleteNotification`,
   не создавая чат и не разбирая содержимое сообщения. Они удаляются из общей очереди уведомлений;
   при последующем создании чата эти пропущенные сообщения не восстанавливаются.
   Сохраняем текущий выбор пользователя; ответы в других созданных чатах продолжаем принимать.
3. Преобразуем событие в сообщение и добавляем его, если оно ещё не было обработано.
   Ответ в неактивном чате сохраняется в нём и становится виден при переключении.
4. После успешной обработки вызываем `DeleteNotification` с полученным `receiptId`.
   Следующее уведомление запрашиваем после завершения подтверждения.
5. Известные события вне текущего функционала, включая вложения, группы, ботов и исходящие события,
   пропускаем и подтверждаем. Эхо нашей отправки не добавляет второе исходящее сообщение.
6. При неопределённом результате подтверждения сохраняем сведения об обработанном событии и сверяем очередь
   через следующий `ReceiveNotification`. Если вернулось то же уведомление, повторяем подтверждение без дубля сообщения.
   Если получено другое событие или пустой ответ, старое больше не удерживает очередь и продолжаем обычную обработку.

Повторное удаление уже отсутствующего уведомления может вернуть `result: false`.
Не ожидаем бесконечно `result: true` для такого уведомления; используем сверку очереди, описанную выше.
Основание: [DeleteNotification](https://green-api.com/telegram/docs/api/receiving/technology-http-api/DeleteNotification/).

Поддерживаем `textMessage` и текст из `extendedTextMessage` для сообщений со ссылками.
Карточки предпросмотра ссылок не строим. Основание:
[текстовое сообщение](https://green-api.com/telegram/docs/api/receiving/notifications-format/incoming-message/TextMessage/)
и [текст с URL](https://green-api.com/telegram/docs/api/receiving/notifications-format/incoming-message/ExtendedTextMessage/).

Сообщение относится к чату по `chatId`, даже если номер собеседника скрыт.
`receiptId` служит только для подтверждения уведомления и не заменяет идентификатор сообщения.
Основание: [ReceiveNotification](https://green-api.com/telegram/docs/api/receiving/technology-http-api/ReceiveNotification/).

### Выход

1. Пользователь завершает локальную сессию.
2. Останавливаем получение, отменяем активные запросы и таймеры повторных попыток.
3. Очищаем учетные данные, чаты, сообщения и черновики, возвращаем форму подключения.
4. Результаты старых запросов больше не могут изменить состояние, в том числе после нового входа в тот же инстанс.

Выход из приложения не выполняет разлогинивание Telegram-инстанса в GREEN-API.
Отмена запроса в браузере не отменяет сообщение, которое API уже успел принять.

## Расчёты и правила целостности

Финансовых расчётов в проекте нет. Вычисляются доступность действий, порядок элементов и признаки повторных событий.

- **Доступность отправки:** активная сессия + выбранный чат + допустимый текст + отсутствие выполняющейся отправки
  в этом чате. Ошибка учетных данных делает сетевые действия недоступными до исправления подключения.
- **Уникальность чата:** один `chatId` соответствует одной переписке в рамках сессии.
  Повторный ввод номера открывает существующий чат; имя собеседника не используется как идентификатор.
- **Уникальность сообщения:** пара `(chatId, idMessage)` в рамках сессии.
  `idMessage` уникален только внутри чата. Пока его нет, используем локальный идентификатор;
  одинаковый текст не является основанием для удаления сообщения как дубля.
  Основание: [идентификатор сообщения](https://green-api.com/telegram/docs/api/message-id/).
- **Время:** время входящего сообщения берём из уведомления, исходящего — из момента локальной отправки.
  Значение `timestamp` из API в секундах переводим в миллисекунды для отображения: `timestamp * 1000`.
  Время показываем в часовом поясе браузера.
- **Порядок сообщений:** по времени от старых к новым; при одинаковом времени сохраняем порядок добавления.
  Обновление состояния отправки не создаёт новую запись и не меняет её время.
- **Порядок чатов:** по времени последнего отображаемого сообщения от новых к старым;
  для пустого чата используем время создания. Текст последнего сообщения вычисляем из переписки.
- **Повтор получения после временного сбоя:** задержка `Math.min(1000 * 2 ** n, 30000)` миллисекунд,
  где `n = 0` для первого сбоя подряд. После успешного запроса счётчик сбрасываем.
  Для ограничений API учитываем указанное сервером время ожидания, если оно предоставлено.
  Эту политику не применяем к автоматическому повтору отправки сообщений или поиска аккаунта.

## Ошибки и восстановление

- Ошибка заполнения формы не запускает запрос; пользователь видит, какое поле исправить.
- Временный сбой получения не удаляет переписку. Показываем состояние соединения и восстанавливаем получение.
- При ошибке учетных данных, настроек или недоступности инстанса приостанавливаем соответствующие запросы,
  объясняем причину. Для повторной проверки получения показываем действие «Повторить получение»;
  для исправления учетных данных пользователь выходит и подключается заново.
- Успешный HTTP-статус сам по себе не означает успешный результат операции: проверяем обязательные поля
  и признаки ошибки конкретного метода. Например, `CheckAccount` может вернуть ошибку в теле ответа.
- При неожиданном формате, который не позволяет безопасно обработать событие,
  показываем ошибку и останавливаем цикл. Такое событие не подтверждаем как успешно обработанное.
  После исправления причины пользователь может запустить цикл действием «Повторить получение».
- Технические сообщения для пользователя не содержат токен и полный URL запроса с учетными данными.

## Критерии готовности основного сценария

1. Пользователь подключается с корректными данными подготовленного инстанса.
2. По номеру телефона создаётся чат; повторный ввод этого номера не создаёт дубль.
3. Текст из приложения приходит собеседнику в Telegram.
4. Ответ собеседника отображается в той же переписке, в том числе после переключения между чатами.
5. Повторное уведомление не дублирует сообщение; сообщение со ссылкой отображается как текст.
6. При ошибке отправки текст сохраняется, а после выхода старые запросы не восстанавливают данные сессии.
