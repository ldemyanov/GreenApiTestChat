# Технологии, архитектура и стиль кода

## Технологии

Ориентир по major-версиям: Vite 6, TypeScript 5, React 19, Vitest 3, ESLint 9, Prettier 3.
React Testing Library + jsdom. Запросы — встроенный `fetch`, отдельные HTTP-библиотеки не ставим.

Не добавлять: react-router, axios, tanstack-query, UI-kit, CSS-in-JS, state-менеджеры вне React.

Скрипты, когда появится каркас: `dev`, `build`, `preview`, `test`, `lint`, `format`. TypeScript проверять через `tsc --noEmit` или скрипт `typecheck`, если он есть.

## Краткое описание архитектуры

Приложение — клиентское SPA на React, которое обращается напрямую к GREEN-API.
Собственный backend и база данных не требуются.

### Структура приложения

- `src/app/` — корневой компонент, переключение между формой входа и чатом, общие стили и CSS-переменные.
- `src/components/` — форма входа, список чатов, форма создания чата, переписка, сообщение и поле отправки.
  Стили размещаем рядом с компонентами в файлах `*.module.css`.
- `src/api/` — типизированные функции GREEN-API и общий модуль запросов на `fetch` с обработкой ошибок и отменой.
- `src/hooks/` — управление сессией, отправкой сообщений и циклом получения уведомлений.
- `src/model/` — типы чатов и сообщений, reducer состояния и преобразование уведомлений API в данные приложения.

### Состояние и взаимодействие с API

Состояние храним средствами React: `useState` для простых значений и `useReducer` для чатов и сообщений.
Общее состояние принадлежит ближайшему общему родителю и передаётся компонентам через props.
Учетные данные и переписку храним в памяти: обновление страницы сбрасывает сессию.
Для двух состояний интерфейса отдельный роутер не нужен.

Отправку выполняем через `SendMessage`, отображаем состояние запроса и сохраняем текст при ошибке.
Автоматически не повторяем отправку после неопределённого сетевого результата, чтобы избежать дублирования.

Получение организуем одним последовательным циклом на сессию:
`ReceiveNotification → обработка → DeleteNotification → следующий запрос`.
Добавляем защиту от повторного добавления сообщений и задержку перед повтором при временных сетевых ошибках.
При выходе отменяем запросы и исключаем обновление состояния ответами предыдущей сессии.

### Проверки

Vitest используем для проверки обработки уведомлений, ошибок и состояния чатов.
React Testing Library и jsdom — для сценариев отправки и отображения сообщений.
Реальную переписку через GREEN-API и внешний вид проверяем в браузере.
До реализации полного интерфейса отдельно проверяем из браузера базовый URL и CORS для всех пяти методов,
перечисленных в `spec/04-green-api-contract.md`.

## Стиль кода

1. Предпочтительная длина строки — 120 символов. Это ориентир для Prettier, а не строгий предел.
2. Отступ — 4 пробела. Символы табуляции не используем.
3. В JavaScript и TypeScript по умолчанию используем одинарные кавычки, в HTML-атрибутах и строковых JSX-атрибутах — двойные. Prettier может выбрать другой вид кавычек, чтобы избежать лишнего экранирования.
4. Параметры стрелочных функций всегда заключаем в круглые скобки, даже если параметр один: `(message) => message.id`.
5. Используем точки с запятой в конце инструкций (`semi: true`).
6. Prettier отвечает за форматирование, ESLint — за проверку кода и правил React. Конфликтующие правила форматирования ESLint отключаем через `eslint-config-prettier`.
